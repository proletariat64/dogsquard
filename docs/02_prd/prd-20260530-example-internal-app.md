# Example Internal App PRD

## Purpose

The example internal app proves that Dogsquard can manage a realistic small project lifecycle from requirements through implementation, tests, PR review, and release discipline.

The app is not the Dogsquard business product. It is a compact test case for the Dogsquard bootstrap kit.

## Non-Goals

- Do not build a production task-management product.
- Do not add authentication in the first implementation phase.
- Do not add a database in the first implementation phase.
- Do not add deployment in Phase 5A or Phase 5B.
- Do not add Playwright in Phase 5A.
- Do not expand the example into a large dashboard product.

## Target User

The target user is the repository owner validating Dogsquard against a realistic internal full-stack application workflow.

Secondary users are future agents working inside repositories initialized from Dogsquard.

## Example Domain

The example domain is Internal Task Intake.

The app lets the user create and manage small internal task or intake records.

## Core User Flow

1. User opens the dashboard.
2. User sees an empty state or existing task records.
3. User enters task details in a form.
4. User submits a valid task.
5. App validates the input.
6. Backend stores the task in memory.
7. Dashboard table shows the new task.
8. User updates task status.
9. User deletes the task when it is no longer needed.

## Frontend Requirements

- Use JS or TS.
- Provide a simple task creation form.
- Display a dashboard table of tasks.
- Support create, list, update, and delete interactions.
- Show lightweight validation messages near the relevant form or action.
- Keep layout simple and functional.
- Avoid adding design-heavy assets or unrelated product surface.

## Backend Requirements

- Use Go.
- Provide an HTTP API.
- Provide a health endpoint.
- Use in-memory storage for Phase 5B.
- Validate incoming JSON.
- Return JSON responses.
- Keep code small and TDD-friendly.
- Avoid database, authentication, deployment, and external service dependencies initially.

## API Outline

Expected endpoints:

```text
GET    /health
GET    /api/tasks
POST   /api/tasks
PATCH  /api/tasks/{id}
DELETE /api/tasks/{id}
```

Expected behavior:

- `GET /health` returns service health as JSON.
- `GET /api/tasks` returns all tasks.
- `POST /api/tasks` creates a task when input is valid.
- `PATCH /api/tasks/{id}` updates supported task fields.
- `DELETE /api/tasks/{id}` removes a task.

## Validation Rules

- `title` is required.
- `title` must not be blank after trimming whitespace.
- `priority` must be one of `low`, `medium`, or `high`.
- `status` must be one of `open`, `in_progress`, or `done`.
- `description` may be empty.
- Invalid API input returns a JSON error response.
- UI validation errors must be visible to the user.

## Data Model

Task fields:

```text
id
title
description
priority: low | medium | high
status: open | in_progress | done
created_at
updated_at
```

`id`, `created_at`, and `updated_at` are generated by the backend.

## Testing Requirements

- Backend unit tests cover validation and task storage behavior.
- API behavior tests cover health, create, list, update, delete, and invalid input.
- Frontend checks cover form validation and dashboard rendering when frontend tooling exists.
- Playwright smoke tests are planned for a later phase, not Phase 5A.
- `make release-check` must continue to pass.

## Documentation Requirements

- Keep this PRD updated when example app scope changes.
- Keep BDD scenarios aligned with user-visible behavior.
- Add or update ADRs if architecture direction changes.
- Add runbooks when local workflow changes.
- Update changelog entries for meaningful project changes.

## Future Expansion Notes

Possible later additions:

- persistent storage
- authentication
- pagination or filtering
- fuller frontend test tooling
- Playwright smoke coverage
- deployment workflow integration

These are intentionally outside the first implementation pass.

## Acceptance Criteria

- PRD defines the tiny Internal Task Intake scope.
- Backend scope is Go HTTP API with in-memory storage.
- Frontend scope is simple form plus dashboard table.
- Validation rules are explicit.
- Data model is small and stable enough for Phase 5B implementation.
- Testing expectations are clear and TDD-friendly.
- Phase 5A remains documentation-only.
